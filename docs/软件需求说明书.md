## 1. 选题与问题定义

### 1.1 使用情境

学生宿舍里每天要重复几十次的动作是"看环境、调设备"：闷了就开风扇、太亮就拉窗帘、睡前关灯关空调。这些动作本身简单，麻烦的是**判断规则只存在于人的记忆里**——换人值班就全忘，忘记关空调就是浪费电。

本作品把这条规则从"记忆"搬到"可编辑的规则"：用户用一句话表达"光照 ≤ 150 lx 且噪声 ≤ 45 dB 时，把顶灯开到 80%、空调开到 26 ℃"，之后由规则引擎按模拟环境数据自动判断、自动执行，并把每次判断的依据写进日志。

### 1.2 目标用户

宿舍舍长、社团值班室管理员这类"要替别人管环境"的学生。

### 1.3 范围

**做**：规则编排、模拟环境、设备联动、冲突裁决、执行日志、场景演练、本地持久化、单元测试。

**不做**（题目明确不要求，也如实写进报告）：真实硬件接入、云平台、多用户账号、3D 建模。

## 2. 功能需求

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| FR-01 | 4 类可控制设备 | 照明（顶灯、床头灯）、温控（空调）、通风（风扇）、遮光（窗帘），共 5 台实例，每台 1~3 个可写属性 |
| FR-02 | 3 项以上可调整模拟环境 | 温度 −10~45 ℃、湿度 0~100 %、光照 0~2000 lx、噪声 0~100 dB，四路滑块实时可调 |
| FR-03 | 不少于 4 条规则，含 1 条双条件 | 内置 6 条，其中 3 条为"两个条件 AND"规则 |
| FR-04 | 规则可新增、修改、启停 | 编辑器支持名称、优先级 1~99、冷却时间、1~2 个条件、1~3 个动作；列表开关即时生效 |
| FR-05 | 规则引擎按实际输入计算 | 给定环境 + 设备 + 规则，返回确定的执行计划（含执行顺序） |
| FR-06 | 记录触发条件、设备变化、执行顺序 | 每条记录含中文条件文本、设备增量、`seq` 顺序号、冲突信息 |
| FR-07 | 冲突时给出明确顺序 | 同一 `deviceId.property` 只允许一条规则生效；优先级降序、同级比创建序号；被抢占动作记入 `conflicts` |
| FR-08 | 不少于 2 组场景演练 | 内置午休 / 夜读 / 离舍 3 组，可一键装载，也可把当前状态另存为自定义场景 |
| FR-09 | 保存设备设置、规则与执行记录 | Preferences 四键 + RDB 一表 |
| FR-10 | 退出重启后恢复 | 强杀进程后冷启动，规则、设备值、环境值、日志全部一致 |

### 2.1 完整业务闭环

新建规则 → 调整 Mock 环境 → 观察设备联动与日志 → 发现冲突并调整优先级 → 保存场景 → 退出重启恢复修改。

## 4. 数据模型

### 4.1 领域对象（`model/Types.ets`）

| 对象 | 关键字段 | 说明 |
| --- | --- | --- |
| `Device` | `id`、`kind`（light/ac/fan/curtain）、`name`、`room`、`power: boolean`、`props: Record<string, number>`、`updatedAt` | 设备属性统一按数值处理，`power` 单独布尔；写入时整体替换以保证 UI 刷新 |
| `EnvSnapshot` | `temperature`、`humidity`、`illuminance`、`noise`、`updatedAt` | 一次 tick 的环境输入 |
| `Condition` / `ConditionGroup` | `source`（env/device）、`key`、`op`、`value`；`logic`（and/or）+ `items` | 条件 AST，支持双条件 AND/OR |
| `DeviceAction` | `deviceId`、`property`、`value` | 冲突消解的最小单位 |
| `AutomationRule` | `id`、`name`、`enabled`、`priority`(1~99)、`cooldownMs`、`createdSeq`、`conditionGroup`、`actions` | 一条"当…就…"规则 |
| `ExecStep` | `seq`、`ruleId`、`conditionText`、`actions`、`skipped`、`cooldownRemainMs` | 计划中的一步，`seq` 即日志中的"顺序 N" |
| `ExecutionPlan` | `steps`、`conflicts`、`records` | 一次 tick 的裁决结果 |
| `ExecutionRecord` | `ts`、`seq`、`ruleId`、`conditionText`、`matched`、`actions`、`conflicts`、`skipped` | 落库流水 |
| `SceneProfile` | `id`、`name`、`env`、`devices`、`createdAt` | 场景快照 |

### 4.2 存储设计

| 存储 | 键 / 表 | 内容 | 选择理由 |
| --- | --- | --- | --- |
| Preferences | `qishe.rules` | 规则数组，外层 `{schemaVersion, rules}` | 体量小、每次整体读写 |
| Preferences | `qishe.devices` | 5 台设备当前状态 | 同上 |
| Preferences | `qishe.env` | 四路环境值 | 同上，写入防抖 400 ms |
| Preferences | `qishe.scenes` | 3 组预设 + 自定义场景 | 同上 |
| RDB | `execution_log` | 执行流水 | 持续增长，需要按时间分页与裁剪 |

`execution_log` 表结构：

```sql
CREATE TABLE IF NOT EXISTS execution_log (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ts INTEGER NOT NULL, seq INTEGER NOT NULL,
  rule_id TEXT NOT NULL, rule_name TEXT NOT NULL,
  condition_text TEXT, matched INTEGER DEFAULT 0,
  actions_json TEXT, conflicts_json TEXT, skipped INTEGER DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_log_ts ON execution_log (ts DESC);
```

`schemaVersion` 当前为 2：版本不符或 JSON 损坏时**回落 6 条种子规则**，不让应用打不开。

## 5. 接口定义

| 接口 | 输入 | 输出 | 异常/边界 |
| --- | --- | --- | --- |
| `RuleEngine.evaluate(input: EngineInput)` | `{env, devices, rules, runtime, now}` | `ExecutionPlan` | 无命中 → 返回一条 `matched=false` 的空计划；不抛异常 |
| `ConflictResolver.resolve(rules, devices, runtime, now)` | 已排序规则 + 快照 | `{steps, conflicts}` | 同 `targetKey` 只认领一次；冷却中跳过但留痕；同值幂等跳过 |
| `ConditionEvaluator.evalGroup(group, env, devices)` | 条件组 + 快照 | `boolean` | 空组/NaN/未知算子 → `false` |
| `RuleValidator.validate(rule, devices)` | 规则 + 设备表 | `{ok, errors[], codes[]}` | 一次返回全部问题（名称空/条件空/优先级越界/孤儿设备/冷却为负/动作为空） |
| `RuleRepository.loadRules()` / `saveRules(rules)` | — | `Promise<AutomationRule[]>` | 读失败回落种子；保存后立即 `flush` |
| `LogRepository.append(records)` / `queryPage(offset, size)` | 记录数组 / 分页参数 | `Promise<void>` / `Promise<ExecutionRecord[]>` | 写失败只记 HiLog，不中断联动；超 500 条裁剪 |
| `EnvStore.clampInto(key, value)` | 环境键 + 原始值 | 新的 `EnvSnapshot` | 越界 clamp；NaN 拒绝 |
| `Boot.start(context)` | UIAbilityContext | `Promise<void>` | 并发读取四键 + count，局部失败用默认值 |

**模块间契约**：唯一跨模块的数据契约是 `EngineInput` 与 `ExecutionPlan`，`now` 由调用方注入而非引擎内部取时间，便于测试构造冷却场景。

**可测性要求**：引擎为纯函数（无 IO、无 UI 依赖），仓储通过 `Prefs` / `LogRepository` 静态入口访问，测试时不启动 UI。

## 6. 测试方案

### 6.1 用例清单（9 条，Hypium 1.0.25）

| # | 类别 | Mock 输入 | 预期结果 |
| --- | --- | --- | --- |
| 1 | 正常 | 28.4 ℃ / 66 % / 140 lx / 42 dB，三条规则启用 | 命中 3 条，顺序 R-94 → R-88 → R-60，`seq` 为 1/2/3 |
| 2 | 正常 | 顶灯亮度已是 80，R-94 目标同为 80 | 该 target 幂等跳过，不入 conflicts |
| 3 | 正常 | R-94 与 R-60 同时写 `d-light-ceiling.brightness` | R-94 生效，R-60 记 1 条 conflict，`keptBy=R-94` |
| 4 | 边界 | 温度 28.0（恰好等于阈值） | 命中（`>=` 含等号） |
| 5 | 边界 | 温度 27.99 | 不命中，空计划 + `matched=false` |
| 6 | 边界 | R-94 冷却 60 s，10 s 后再次触发 | `skipped=true`，动作清空 |
| 7 | 异常 | 环境温度为 `NaN` | 判为不满足，不抛异常 |
| 8 | 异常 | 条件组为空数组 | 校验失败，`EMPTY_CONDITION` |
| 9 | 异常 | 存储中 `schemaVersion=1` / JSON 损坏 | 回落 6 条种子规则 |
